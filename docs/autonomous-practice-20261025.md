# private-isu 自動改善の実験と ISUCON15 の準備材料

記録日: 2026年10月25日 日本時間

今回の目的は、private-isu の続きを使って、AIが調査・変更・検証・記録をどこまで自律的に進められるか確かめ、ISUCON15に持ち込む運用を選ぶこと。ISUCON15側のリポジトリ、CI/CD、Webhook、AGENTS.md、Skillsは変更していない。

ローカル環境の標準初期化・再起動・ベンチ反復はユーザーが明示許可した。コメント件数の一括化、投稿詳細の画像BLOB取得省略、標準ライブラリによるハッシュ計算、テンプレートの再利用、DB接続数の比較まで進めた。実測値と検証範囲は末尾の記録を参照。スコアが上がったと確認できない施策も、その事実を残している。

## 最終結果

**5施策を検証し、最終構成は44,429点、pass true、fail 0。** 標準ベンチは12回すべて成功し、そのうち1回はCPUプロファイル付きの診断試行。ホストとDockerで最終の12テストが成功した。

接続数だけを変えた1→4→1→4の比較は、32,543→36,318→27,317→44,429点。今回の各2回では4接続の方が高かったため採用した。ただしMacは他の作業とCPU・メモリを共有しており、改善率や他環境での再現性は確定していない。初回基準41,801点や以前の約5.3万点を使って一括した改善率は算出しない。

コードは `practice/autonomous-prep-20261025` にローカルコミット済み。実装を含む最新コミットは `75d3d10`、app本体の最新変更は `2be1edd`。通常のComposeで起動する `private-isu-app:latest` に最終イメージを反映済み。推論による候補と実測した結果は以下で分けている。

## ログから選んだ最初の仮説

前回の `log/top-comment-users-20261023-182911/after-run.json` に保存されたバイト位置を使い、2026年10月23日18:34:48〜18:35:59 JSTのベンチ1回の範囲だけを既存ログから取り出した。元ログの消去・移動・権限変更はしていない。HTTP時間はリクエスト時間の累積であり、ベンチの経過秒数ではない。

| HTTP経路 | 件数 | 累積時間 | 平均時間 |
| --- | ---: | ---: | ---: |
| GET `/` | 2,076 | 205.672秒 | 99ms |
| GET `/posts` | 260 | 97.015秒 | 373ms |
| GET `/posts/:id` | 2,089 | 58.857秒 | 28ms |
| GET `/@account` | 350 | 54.669秒 | 156ms |
| POST `/login` | 1,526 | 17.998秒 | 12ms |

同区間のSQL累積時間は約16秒。コメント一覧取得50,410回・約2.69秒、投稿別コメント件数52,499回・約2.61秒、個別ユーザー取得55,258回・約2.31秒を観測した。これらは全ルート合計で、トップページだけの数字ではない。SQL時間の割合をHTTP時間の割合として扱わない。

`webapp/node/src/app.ts` のGET `/` は投稿と作者をJOINで20件取得し、各投稿で最新3コメントと全コメント件数を取得していた。`connectionLimit: 1` なので、2つのSQLを `Promise.all` に並べてもDB接続が同時に2本動くわけではない。

今回の仮説は「投稿別のCOUNTを、表示対象IDの `IN (?) GROUP BY post_id` にまとめれば、DBとの往復と接続待ちを減らせる」。記事にある一括取得の方向性を、現在のボトルネックに限定して適用した。N+1削減、キャッシュ、ファイル配信、ハッシュの外部コマンド置換などの候補は、[Gurriumの実践記](https://giarrium.hatenablog.com/entry/2023/12/17/130000)にもある。記事の環境はEC2上のGo実装なので、その得点や改善率は今回には移さない。

## 実装と確認結果

変更はGET `/` のコメント件数取得だけ。対象投稿のIDを集めて1回集計し、`Map<post_id, count>` から補完する。0件の投稿はGROUP BY結果に出ないため、既定値を0とする。投稿が0件なら集計SQL自体を発行しない。

最新3コメントの取得・逆順表示、作者補完、BAN済み投稿の除外、認証、初期化、DB構造は変更していない。Go/Ruby/PHP/Pythonの対応する表示組み立ても確認し、「総数は全コメント、表示は最新3件を時系列順」という契約と整合する変更に限定した。他言語の実行検証はしていない。

未ログインのトップページ20投稿に対する表示SQL数は、コメントありの場合42→23、全投稿コメントなしの場合41→22。これはコードとモック検証で確認した回数であり、実DBの新規計測結果ではない。

検証は `webapp/node/test/homepage-counts.test.mjs` に残した。実ハンドラとEJSを通し、投稿0件、コメント0件、総数7件でも表示は3件、20投稿でコメント0〜4件が混在するケースを確認する。集計結果の順序を逆にしても、投稿IDごとの件数が一致することを確かめた。このテスト自体はSQLをモックする。後続の実DB照合でもHTML一致とSQL回数削減を確認済みで、実行計画は末尾に記録した。

ローカルとDocker内でビルドと9テストが成功。テスト時だけNodeの実験的module mockingフラグを使う。Dockerの比較用イメージも両方ビルド済み。

## 今回見つかった運用上の問題

### コマンド名や説明だけでは副作用が分からない

`Taskfile.yml` の `analyze` は「元ログは保持」と表示するが、実際にはログ移動、nginxのreopen、MySQLのflush-logs、権限変更も実行する。`docs/local-practice.md` に残っていた「移動せず、ローテーションも行わない」は今回訂正し、読み取りだけの解析コマンドを追記した。今回このタスクは使わなかった。

将来は `analyze` を読み取りに限定し、`rotate-logs` を別の操作にするか、明確に副作用を表示する。これは未実装の提案。

### ベンチの点数には動いている版が必要

GitのHEADだけでは、停止前にビルドされたDockerイメージや、DB索引、生成済み画像は分からない。今回も比較用イメージを別タグで作成した。実際に動かすときはイメージIDとコンテナ内ソースのハッシュを記録する。

前回のコメント作者一括化はSQL数を減らしたが、記録上のスコアは変更前55,510／52,770、変更後53,117／53,118で、向上を確認できなかった。この事実からも、SQL数の削減とスコア向上を分けて判断する必要がある。

### 自律実行の境界を開始時に指定すると止まりにくい

標準ベンチの初期化が追加投稿・コメントを削除するため、開始時に一度確認を挟んだ。その後、ユーザーがローカル初期化・再起動・ベンチの反復を明示許可した。以降はこの範囲で再確認せず進める。共有サーバーへその許可を拡張しない。

## ISUCON15へ持ち込む運用案

以下は今回の経験と参加者の報告からの提案であり、チームで採用済みの決定ではない。本番の言語、DB、サーバー台数、ベンチ受付方法、AI利用条件は当該大会のマニュアルで確定する。

優先したいのは、**指定した変更を反映し、起動を確認し、一度だけベンチを実行し、同じ場所へ証拠を保存する手順**。通知やCIの見た目はその後に置く。[to-hutohuの発表](https://speakerdeck.com/tohutohu/findy-isucon-2024-11-14)は、手軽な準備として1コマンドのデプロイスクリプトを挙げ、CDを必須にしていない。一方で[ぽよメモのISUCON12本戦記](https://poyo.hatenablog.jp/entry/2022/08/28/191329)は、計測と結果回収までまとめたことで、実行者以外も調査しやすくなったと報告している。

| 優先度 | 用意するもの | 満たしたい条件 |
| --- | --- | --- |
| 最優先 | 状態確認 | 対象環境、HEAD、差分、稼働版、資源制限、進行中ベンチを表示 |
| 最優先 | 反映と復元 | コミットと設定を指定し、同じ成果物へ戻せる。DB・生成ファイルは別途扱う |
| 最優先 | 起動確認 | ビルド成功やプロセス存在だけで進めず、期限付きで実HTTPと依存先を確認 |
| 最優先 | ベンチと採取 | 反映開始から終了後採取まで環境単位で排他。失敗時も結果保存 |
| 次 | 比較レポート | 成功判定、score、fail、メッセージ、対象版、主要なHTTP/SQLを前回と比較 |
| 次 | CI | ビルド・小さな契約テスト。ベンチ判定は終了コードと結果JSONの両方を確認 |
| 後 | Discord等の通知 | 完了・失敗・判断が必要な結果とレポート先だけ送る |

想定する実行順は `状態確認 → 排他取得 → 指定版を反映 → 起動確認 → ログ範囲を記録 → ベンチ → 成否にかかわらず証拠回収 → 比較 → 排他解除`。計測中に他の変更が混ざれば比較不成立として残す。読み取り調査は並列化できるが、共有環境への反映と計測は一つの担当に集める。

GitHub Actionsだけで排他を制御しても、手元のSSH操作は制限できない。したがって、もしActionsから実行する場合も、全員が通る同じデプロイ・計測コマンドに環境単位の排他を設ける。これは今回の設計提案で、実装・実地検証は未実施。

ログは試行IDごとに保存し、最低限次を対応させる。

```text
run_id / 開始終了日時 / 対象URLとホスト
仮説 / 変更コミット / 未コミット差分の有無
稼働イメージまたはバイナリのハッシュ / 設定のハッシュ
ベンチ実装と引数 / 初期化方法 / CPU・メモリ条件
exit_code / pass / score / fail / messages
HTTP集計 / SQL集計 / 資源観測 / エラーログの保存先
採用・保留・復元 / 次の仮説
```

今回のバイト位置での切り出しはログを消さない利点があるが、途中のローテーションや切り詰めには弱い。自動化する場合はinode・開始サイズ・終了サイズを確認し、変化した区間を正常なデータとして扱わない。アクセスログのバッファリングがあれば終了直後の採取漏れにも注意する。

## AGENTS.md と Skills の役割案

AGENTS.mdには、常に守る短い規則と手順へのリンクを置く。記事一覧、長いコマンド例、全ベンチ結果を詰め込まない。今回の共通方針はすでに [isu-conのAGENTS.md](../../AGENTS.md) にあるため、複製する前に役割を整理する。

当日用に決める項目は次のとおり。

- 対象ホスト・リポジトリと、他メンバーが作業する場所。
- 自律的に実行できる範囲。標準初期化、再起動、反映、コミット、push、連絡を個別に指定する。
- 仕様の根拠と、絶対に維持する動作。キャッシュの更新・初期化・再起動後の整合性も含める。
- 「1仮説→1変更→検証→コミット→計測→判断」の単位。
- デプロイ・計測の排他、実行するコマンド、失敗時に止める条件。
- 最新結果と再開地点を読むファイル。

Skillsへ切り出す候補は、今回のような手順を何度か成功させてから選ぶ。

| 候補 | 入力と成果物 | 含めないもの |
| --- | --- | --- |
| ベンチ実行 | 対象・版・試行名 → 結果JSONと証拠一式 | 任意のDB再インポート、勝手な共有環境切替 |
| ログ解析 | 試行ディレクトリ → 重いHTTP/SQL、仮説3件以内 | 勝手な反映・ログ消去 |
| 改善検証 | 仕様と1仮説 → 最小差分、契約確認、比較結果 | 複数案の同時採用 |

[trastaのISUNARABE実践記](https://trasta.dev/blog/20260509)には、競技中にベンチ実行とログ分析をSkillsにまとめた例がある。別大会のポータルAPIや認証方式をそのまま流用する根拠にはならない。[ichyoの実践記](https://blog.ichyo.jp/posts/isunarabe2026)の参加者本人の準備記述は、設定を含めた成果物とデプロイの排他を重視している。後半は記事内でAI執筆と明示されているので、AIの自己評価と参加者本人の証言を混同しない。

## 最初に設定した検証手順

1. ローカル環境で基準イメージを起動し、既存DBが利用できることとHTTP 200を確認する。
2. 変更前後のハンドラを同じ実DBへ接続し、コメントあり・なし・混在・投稿0件のHTMLと総数を比較する。この実DB照合は後続の作業で実施済み。
3. 基準→変更後で標準ベンチを実施。差が小さければ逆順でも繰り返し、版・ログ区間・エラーを保存する。
4. 効果が確認できたら採用。判別できなければ保留として、残る最新コメント取得、GET `/posts` の過剰取得、投稿詳細の画像BLOB転送、同期ハッシュ処理をログに沿って選ぶ。

投稿詳細とハッシュ計算は後続の作業で実装・検証した。GET `/posts` はBAN済み投稿を除いた後で20件必要なので、単に元SQLへLIMIT 20を付けるだけでは表示件数が減り得る。記事の解法を当てる際も、このような対象固有の条件を先に確かめる。


## 標準ベンチ開始後の記録

ローカル操作の許可を受け、既存DBボリュームでComposeを起動した。DB再インポートは行っていない。MySQLは9.7.2、Node.jsは24.22.1。試行は変更していない標準ベンチの60秒負荷＋10秒待機。appとMySQLは各1CPU・1GiBで固定し、DB・Memcachedは試行間に再起動していない。appを差し替える際はnginxをreloadし、HTTP 200を期限付きで待ち、稼働ソースのSHA256を対象コミットと照合した。

コメント件数一括化は、実DBを使う4ケースで変更前後のHTML完全一致を確認した。投稿一覧の最初の結果だけを実DB由来の投稿群に差し替え、残るコメント・ユーザー・件数SQLはMySQLで実行した。20投稿でコメント60件、混在30件、コメント0件、投稿0件を含む。SQL数は42→23、42→23、41→22、1→1。集約SQLは `idx_post_id_created_at` のcovering index range scanを使用していた。

最初の試行順は基準→件数一括化→件数一括化→基準。41,801→27,023→31,672→31,188点で全回pass・fail 0・messages空だった。2回目は最初のログ解析と時間が重なっており探索用の値として扱う。基準へ戻しても低い値になったため、一括化が初回差の原因とは断定しない。SQL削減と正しさを根拠に変更を保持するが、スコア向上は未確定。

ビルドの落とし穴もあった。Nodeディレクトリには `.dockerignore` がなく、Dockerfileの `COPY . .` によりホストのnode_modulesが入る可能性がある。主要依存バージョンはlockfileと一致していたものの、それだけで同じ成果物とは保証できない。以降は `git archive <commit> webapp/node` でコミットの内容だけを取り出し、同じDockerfile・依存lockfileでビルドする。今回のスコア変動の原因がこれだとは確定していない。

### ハッシュ計算の外部プロセスをなくす

`digest` はシェル・OpenSSL・sedを同期起動し、ログイン/登録ごとに2回呼ばれる。Node標準の `crypto.createHash('sha512').update(src, 'utf8').digest('hex')` へ置換する。二重SHA-512の連結形式、salt、保存形式は変更しない。Go/Ruby/PHP/Pythonのsaltと連結方法も確認した。UTF-8入力とhex出力の仕様は [Node.js 24のCrypto仕様](https://nodejs.org/docs/latest-v24.x/api/crypto.html#hashupdatedata-inputencoding) と照合した。

変更前の外部コマンド版と変更後の両方で、OpenSSLから別途作った期待ハッシュによるログインを確認した。英数字、引用符・シェル記号、日本語・絵文字・改行、空文字、4KiB文字列、誤パスワード、存在しないユーザー、登録直後のログインを含む。DBはモックで、実ハンドラ・セッション処理を通す。Dockerでビルドと11テスト成功。新たな依存は追加していない。

ハッシュ置換 `0f2a896` は29,148点、pass・fail 0・messages空。CPUプロファイル付きの診断試行は32,050点だったが、採取の負担を含むので通常試行の比較値にしない。ホストの観測例はload average 14.20、CPU約81%使用、空き物理メモリ約160MB、圧縮メモリ約9GB。ホスト負荷が変動の原因だと断定はできないが、この状態では数%の差を改善率として主張しない。

### EJSのコンパイル済みテンプレートを再利用する

Node inspectorの75秒CPUサンプルでは、idle約45.8秒、EJSに直接属するフレーム約4.29秒、mysql2約4.27秒、GC約2.05秒だった。サンプル上の時間で、各処理の厳密な実行時間や原因の証明ではない。EJSではcompile、scanLine、ソース生成が上位にあり、実装上もrenderのたびにファイル読取と再コンパイルをしていた。

`renderFile` の明示オプションに `cache: true` を渡す。キャッシュ対象はコンパイル済み関数で、HTMLやユーザーデータを保存しない。インストール済みEJS 6.0.1の `handleCache` と `renderFile` の実装を確認した。テンプレート変更の反映にはappの再作成/再起動が必要になる。DB初期化でコンパイル結果を消す必要はない。

コンパイル呼出しを数え、2回目には再コンパイルせず、投稿本文とコメントの変更が即座にHTMLへ出ることを検証した。既存テストと合わせて12件成功。実DBの4ケースでも、キャッシュなし/ありのHTMLが完全一致。

テンプレート再利用 `cf3f343` の標準ベンチは32,543点、pass・fail 0・messages空。直前の通常試行29,148点より高いが、ホスト負荷変動を除去していないため改善率は確定しない。再コンパイルが省かれ、動的データが更新されることは個別テストで確認済み。

### DB接続プールを1から4へ変更する

CPUプロファイルの待機と、MySQLのCPU使用率が1コアの約25〜32%にとどまる観測から、単一接続の待ち行列を疑った。`connectionLimit` だけを1→4にする。資源制限・SQL・索引・データ・ベンチ引数は変えない。待機時間だけでDB接続待ちと確定はできないので、ベンチ結果で判断する。

既存DBの外部キーは0件。`dbInitialize` のPromise.allが複数接続で実行されても、削除順序を要求する外部キー制約はない。ルートの書込み完了をawaitする処理も維持。実DBの索引はposts(created_at)、comments(post_id, created_at)、comments(user_id)、users(account_name)と各主キーで、この実験中には追加・削除していない。Dockerのビルドと12テストが成功。実負荷時の初期化と正しさは標準ベンチで確認する。

### GET /posts の過剰取得

`posts JOIN users` で `del_flg=0` を条件に入れ、その後 `ORDER BY created_at DESC LIMIT 20` を適用する。先に投稿だけを20件へ絞るとBAN済み投稿の分だけ表示が不足する。本文と画像データを全件取得する方式や、ベンチ日時に限定した処理は使わない。
